# TutorLoft — Codex Build Handoff

**Purpose:** This file is the single source of truth for an autonomous coding agent (Codex) building **TutorLoft** (working codename: tutorapp-v2) in a loop. Follow the **Loop Protocol** (§10) exactly. Do not deviate from the locked decisions in §1 without a human instruction in this file.

---

## 1. Product & Locked Decisions

**TutorLoft** is an LMS + billing tool for a **single tutor** (the admin) teaching students, with optional read-only parent accounts. It replaces spreadsheets and Google Classroom for one tutoring practice.

**Branding (locked):** Product name **TutorLoft**, written as one word, capital T and L. Wordmark: "TutorLoft" in Instrument Serif italic with "Loft" in `text-primary` (v1 accent-word pattern). Use the name in the landing hero, page `<title>`s ("… · TutorLoft"), email subjects, invoice header, and README. Default `invoice_prefix` setting: `TL` (numbers like `TL-202607-0001`). Package name in package.json: `tutorloft`.

**Locked decisions — do not change:**

| Decision | Value |
|---|---|
| Tenancy | Single tutor (admin). Students + parents as users. No multi-tenant logic. |
| Hosting | Vercel free tier (Hobby). Must fit free-tier limits. |
| Framework | Next.js (latest stable, App Router) + TypeScript strict + Tailwind CSS + shadcn/ui |
| Database | SQLite via **Drizzle ORM + libSQL client**. Local dev: `file:./data/dev.db`. Prod: Turso free tier via `DATABASE_URL` + `DATABASE_AUTH_TOKEN`. |
| Auth | Auth.js (next-auth v5) Credentials provider. bcrypt password hashes. JWT session cookies. Invite-code onboarding. No OAuth. |
| Payments | **Invoice tracking only.** No payment gateway. Tutor records payments manually (cash/bank/bKash reference). |
| AI | **Optional, BYOK.** Providers: **OpenRouter (recommended default), Anthropic, OpenAI, Google** — all via plain `fetch`. App is 100% functional with zero AI keys. Keys entered by tutor in Settings, stored encrypted in DB, never in env vars or client code. |
| File uploads | Optional. Default submission types: text + URL link. If `BLOB_READ_WRITE_TOKEN` env var exists, enable file upload via Vercel Blob (`@vercel/blob`). Feature-detect at runtime. |
| Email | Optional. If `RESEND_API_KEY` exists, send emails (invites, invoice notices). Otherwise show copyable text/links in UI instead. Feature-detect at runtime. |
| Testing | Vitest (unit) + Playwright (e2e smoke). CI = `npm run check`. |

**Dependency policy:** minimal. Before adding any npm package not listed above, ask: can this be done in <100 lines of app code? If yes, write the code. Allowed without question: `drizzle-orm`, `drizzle-kit`, `@libsql/client`, `next-auth@beta`, `bcryptjs`, `zod`, `date-fns`, shadcn/ui + its Radix deps, `@vercel/blob`, `resend`. AI calls use plain `fetch` — **no AI SDKs**.

**Non-goals (do not build):** payment gateways, video conferencing, real-time whiteboard (may be ported later from v1 — leave a `/whiteboard` route stub only), mobile apps, multi-language i18n, multi-tutor tenancy.

## 2. Roles & Access

| Role | Capabilities |
|---|---|
| `tutor` (admin, exactly one) | Everything: manage students, courses, schedule, billing, content, quizzes, announcements, grading, settings, AI keys. |
| `student` | See own courses, schedule, materials, quizzes (take), assignments (submit), announcements, own invoices/balance, own grades. |
| `parent` | Read-only view of linked student(s): schedule, attendance, invoices/balance, grades, announcements. Cannot submit or take quizzes. |

Rules:
- The first account is created by a seed script (`npm run seed`) from `TUTOR_EMAIL` + `TUTOR_PASSWORD` env vars; role `tutor`.
- Students/parents register only via single-use invite codes generated by the tutor. Invite embeds role and (for parents) linked student ID.
- Every server action / route handler must check session role. Students/parents can only read rows scoped to their own ID. Centralize in `src/lib/authz.ts` (`requireTutor()`, `requireUser()`, `scopeToStudent()`).

## 4. Data Model (Drizzle / SQLite)

All tables: `id` (text, nanoid), `created_at`, `updated_at` (unix ms). FKs with `ON DELETE` as noted. Money stored as **integer minor units** (e.g. cents/poisha) with a global `currency` setting (default `BDT`). Never floats.

Answer/option JSON shapes (validate with zod in `src/lib/quiz-schemas.ts`):
- `mcq_single`: options `["A","B",...]`, answer `{ index: 2 }`
- `mcq_multi`: answer `{ indexes: [0,2] }`
- `true_false`: answer `{ value: true }`
- `short_answer`: answer `{ accepted: ["paris","paris, france"], caseSensitive: false }` — autograde by normalized match; unmatched → flag for manual grading.

## 5. Feature Specs by Phase

Build phases **in order**. Each phase has acceptance criteria — all must pass before checking it off in §10.

### P0 — Scaffold
- `create-next-app` (TS, Tailwind, App Router, src dir), shadcn/ui init, Drizzle + libSQL wired, drizzle-kit migrations, Vitest + Playwright configured.
- Scripts in package.json: `dev`, `build`, `check` (= typecheck + lint + `vitest run`), `e2e` (Playwright), `db:generate`, `db:migrate`, `seed`.
- `.env.example` documenting: `DATABASE_URL`, `DATABASE_AUTH_TOKEN`, `AUTH_SECRET`, `TUTOR_EMAIL`, `TUTOR_PASSWORD`, optional `RESEND_API_KEY`, `BLOB_READ_WRITE_TOKEN`.
- **Accept:** `npm run check` passes; `npm run dev` renders a landing page; migrations create all §4 tables; seed creates tutor.

### P1 — Landing Page, Auth & Invites
- **Landing page at `/` (public entry point).** See §6.5 for full design guidance. Structure: (1) hero — display-serif headline stating the value ("One place for your classes, materials, and billing"), subline, primary CTA "Log in" + secondary "Request access" (mailto or simple contact section — there is NO public signup; accounts are invite-only); (2) three feature cards: Classes & Materials, Quizzes & Assignments, Billing for Parents; (3) "How it works" for students/parents in 3 steps (get invite → join → learn/track); (4) footer with tutor contact. Static server component, zero client JS beyond the nav. Proper `<title>`, meta description, OG tags. Logged-in users hitting `/` are redirected to their role home.
- Login page (email+password). Session role routing: tutor → `/dashboard`, student → `/home`, parent → `/overview`.
- Tutor can create invites (choose role; parent invites pick linked student). Invite page `/join/[code]`: set name+password, account created, invite consumed. Expired/used codes rejected.
- If email enabled, invite is emailed; otherwise tutor gets a copyable link.
- **Accept:** e2e: tutor logs in; creates student invite; student registers via link and lands on `/home`; student cannot open `/dashboard` (redirect); wrong password rejected.

### P2 — Students, Courses, Enrollment
- Tutor CRUD: students list (name, email, status, linked parents, balance placeholder), courses CRUD, enroll/unenroll students, archive instead of delete everywhere.
- Student `/home`: lists enrolled courses.
- **Accept:** e2e covers create course → enroll student → student sees course. Unit tests for authz scoping (student A cannot fetch student B's data).

### P3 — Schedule & Attendance
- Tutor defines weekly `schedule_slots` per course. "Generate sessions" action materializes `class_sessions` for the next N weeks (idempotent — no duplicates for same slot+datetime).
- Sessions list/calendar week view. Tutor marks session done/cancelled and takes attendance (defaults all enrolled to present, toggle per student).
- Student/parent see upcoming sessions and attendance history.
- **Session notes:** per session, `notes_private` (tutor prep/observations) and `notes_shared` ("what we covered today" — visible to student and parent). Parents seeing shared notes is a key trust feature.
- **ICS calendar feed:** per-user read-only URL `/api/ics/[token]` (random `ics_token`, regenerable) serving upcoming sessions as an iCalendar file — subscribable from Google Calendar/phone. Hand-roll the ICS text (~40 lines), no library.
- **Accept:** unit test: session generation idempotency; attendance unique per (session, student); ICS output parses (test escaping + UTC times). e2e: mark attendance + shared note, student sees both; private note invisible to student.

### P4 — Billing
- Rate plans CRUD. Enrollment resolves plan: enrollment override → course default.
- **Prepaid packages** (standard tutoring billing model — TutorBird/Teachworks parity): plan type `package` = N sessions for a fixed amount. "Sell package" creates an invoice + `package_purchases` row. Attended sessions consume active package credits (oldest first) **before** billable per-session lines during invoice generation. Student/parent see remaining credits; tutor warned at ≤2 remaining.
- **Invoice generation action** (per student, for a month): 
  - `per_session` plans: one line per attended (`present`/`late`) session in period × unit amount.
  - `monthly_flat`: one line per active enrollment.
  - Creates `draft` invoice; regenerating a draft for same period replaces items; never touches non-draft invoices. "Generate all" button runs it for every active student.
- Invoice lifecycle: draft → sent → paid/partial (derived from payments sum) → or void. Record payment modal (amount, method, reference, date).
- Invoice detail = clean print-friendly page (print stylesheet; that is the "PDF" — no PDF lib).
- Student/parent billing page: invoice list + outstanding balance. If email enabled, "send invoice" emails a link.
- Dashboard tiles: outstanding total, overdue count, collected this month.
- **Accept:** unit tests: line-item math from attendance fixtures, partial-payment status derivation, idempotent regeneration, sequential invoice numbers, package credit consumption order + exhaustion (attended sessions beyond credits become billable lines). e2e: generate → record payment → status `paid` → student sees paid invoice; sell package → attendance consumes credit → remaining count updates.

### P5 — Course Material Builder (key feature — invest here)
This is the heart of the app for teaching. A course is a structured curriculum, not a file dump.

**Structure:**
- Each course has ordered **modules** (units/chapters); each module has ordered **materials** (`lecture` or `study`). Unassigned materials sit in an "Ungrouped" section. Drag-free reordering is fine (up/down buttons or a sort-order field editor) — don't add a DnD library unless trivial.
- **Curriculum view** for the tutor: whole course outline on one screen — modules, their materials, status chips (draft/scheduled/published), per-material student-completion counts. This is the primary content workspace.

**Authoring:**
- Markdown editor: textarea + always-visible side-by-side live preview (tiny renderer like `marked`, sanitized). Support headings, lists, tables, code blocks, images by URL.
- **Embeds:** material links have a `kind`. `youtube` renders an inline privacy-friendly embed (youtube-nocookie iframe, parse ID from any YT URL form); `pdf` renders an inline `<iframe>`/object viewer; `link` renders a labeled card. If blob enabled, image paste/upload into markdown.
- Draft / publish / scheduled `publish_at` (read-time enforced). Module-level publish toggles all visibility beneath it.
- **Duplicate**: copy a material (or whole module) within or across courses — tutors reuse curriculum every year.

**Student experience:**
- Course page tabs: **Curriculum / Quizzes / Assignments / Announcements**. Curriculum tab shows modules → materials with completion checkmarks and a course progress bar.
- "Mark as complete" per material (writes `material_progress`); auto-mark on quiz submit when a quiz is linked to a material's module.
- Optional **sequential gating**: if `requires_material_id` is set, the material is locked until the prerequisite is completed (server-enforced, not just UI).
- Prev/next navigation between materials in module order.

**Lesson plans (tutor-facing planning layer — works fully without AI):**
- Material type `lesson_plan`, `visibility` defaults `tutor_only` (teaching prep, not student content; tutor can flip to `students` to share). One lesson plan typically sits alongside the lectures/materials of its module.
- Structured editor backed by `plan_json` (zod schema in `src/lib/plan-schema.ts`), sections all optional/toggleable: learning objectives, standards (picked from library), duration & pacing (minutes per section), prior knowledge, vocabulary (term+definition), materials needed, warm-up/hook, direct instruction, guided practice, independent practice, assessment/exit ticket, homework, differentiation notes. Render to markdown for display/print; keep `plan_json` canonical.
- Print-friendly page + "Download .md" for any material (lesson plans especially).
- Material type `worksheet`: student-facing markdown practice sheet (activities like match/fill-in/practice problems written in markdown), printable.

**Standards library & coverage (Monsha-style, minimal):**
- Tutor CRUD for standards: framework label (e.g. NCTB, Cambridge, custom), code, description. Bulk paste import (one per line, `CODE<TAB>description`).
- Tag materials and quizzes with standards (multi-select).
- **Coverage view** per course: standards × modules matrix — where each standard is addressed, untagged standards highlighted as gaps. One table, no charts.

**Tutor insight:** per-course progress matrix (students × materials, completed or not) — one simple table, no charts required.

- **Accept:** e2e: create module → two materials → publish → student completes #1 → gated #2 unlocks → progress bar updates → tutor matrix shows it. Draft/scheduled invisible to student. Duplicate module across courses carries materials + links. Lesson plan created via structured editor renders/prints; `tutor_only` material returns 403 for students; standards tagged on a material appear in coverage matrix with gaps highlighted. Unit tests: XSS sanitization, YT URL→ID parsing (watch/share/shorts/embed forms), server-side gating (403), plan_json↔markdown rendering, standards bulk-paste parser.

### P6 — Quiz Builder & Taking
- Builder: create quiz, add/reorder/edit questions of the 4 types, set points, options, answers. Settings: open/close window, time limit, attempts, shuffle. Preview mode for tutor.
- Taking: student starts attempt (within window, attempts left), one page with all questions (autosave answers every 15s + on change via server action), countdown if time-limited, submit → autograde immediately. Time-expired attempts auto-submit on next interaction/load.
- Grading: autograded types scored instantly; short-answer mismatches queue for manual grading (tutor UI to award points + comment). `final_score` = auto + manual.
- Results: student sees score + per-question correctness after grading complete. Tutor sees table of attempts per quiz + CSV export.
- **Accept:** unit tests: autograder for all 4 types incl. multi-select partial=wrong, normalization for short answers, shuffle determinism per attempt (seed = attempt id). e2e: full take-and-grade flow. Attempt limits and window enforced server-side.

### P7 — Classroom Feed (Announcements, Assignments, Submissions)
- Announcements: tutor posts (all-courses or per-course), markdown, scheduled publish. Students/parents see feed, newest first.
- Assignments: tutor creates with due date, points, allowed submission types. Student submits (text and/or link; file if blob enabled), can resubmit until graded. Late submissions flagged.
- Grading: tutor sees per-assignment submission table (submitted/missing/late), opens each, sets grade + markdown feedback, returns it. Student sees grade + feedback. **Comment bank:** tutor's reusable snippets insertable into feedback (manage in settings; one dropdown, no fuzzy search needed).
- **Comments (Classroom parity):** announcements with `allow_comments` get a class-visible comment thread (students + tutor). Each submission gets a **private** student↔tutor comment thread. Plain text, newest last, no nesting/reactions/editing — delete only (author or tutor).
- **Gradebook:** per-course table — students × (assignments + quizzes), each cell the grade/score, row averages, missing highlighted. CSV export. This is the tutor's marks overview and feeds progress reports.
- **Accept:** e2e: announce with comments on → student comments → tutor sees it; assignment → submit → private comment exchange → grade with comment-bank snippet → student sees feedback; gradebook reflects quiz + assignment grades and exports CSV. Unit: late flag logic; one submission row per student; authz — student A cannot read B's submission comments.

### P8 — Automations
All automations run in a single Vercel cron hitting `/api/cron` (daily, free tier allows this) plus lazy checks at read-time. `/api/cron` is idempotent and guarded by `CRON_SECRET`.
- Auto-generate next 4 weeks of sessions from active slots.
- Auto-mark invoices `overdue` presentation state when past due (derived, not stored).
- On the 1st: auto-create draft invoices for previous month for all active students (skip if exists).
- Auto-close quizzes past `close_at`; auto-publish scheduled materials/announcements (also enforced at read time so cron is optional).
- **Payment reminders:** for invoices `sent` and past due — if email enabled, auto-send one reminder at due+3d and due+10d (log in `activity_log`, never more than one per invoice per cron day); always show a "copy reminder message" button on the invoice (pre-filled Bangla/English text with amount + link) for WhatsApp/SMS use.
- If email enabled: daily digest to tutor (today's sessions, ungraded queue, overdue invoices).
- **Accept:** unit tests calling the cron handler twice on fixtures → identical state (idempotency). Everything still works with cron never firing (read-time enforcement).

### P9 — AI Assist (Optional, BYOK)
Settings page: provider (`openrouter`|`anthropic`|`openai`|`google`), API key, model name (free-text with sensible per-provider placeholder; for OpenRouter e.g. `anthropic/claude-sonnet-4.5`). **OpenRouter is the recommended default** in the UI — one key covers every model. Key encrypted at rest (AES-256-GCM, key derived from `AUTH_SECRET` via HKDF — implement in `src/lib/crypto.ts`, ~40 lines, node:crypto only). Show only last 4 chars after save. "Test key" button.

`src/lib/ai/provider.ts`: one interface `complete({system, prompt, maxTokens}): Promise<string>` with four plain-`fetch` implementations. OpenRouter and OpenAI share the chat-completions shape (OpenRouter = `https://openrouter.ai/api/v1/chat/completions` with `HTTP-Referer`/`X-Title` headers); Anthropic Messages API; Google Gemini generateContent. No SDKs. Timeouts + friendly error surface (invalid key, rate limit, model not found each get distinct messages).

**Shared plumbing for all AI features:**
- **Source materials** (`src/lib/ai/sources.ts`): every generator accepts optional sources — (a) pasted text, (b) a URL (server-side fetch, strip to readable text, cap ~15k chars), (c) one or more existing course materials, (d) a YouTube URL (fetch the watch page and extract available caption text if trivially possible; otherwise prompt tutor to paste the transcript — do NOT add a transcript library). Multiple sources concatenate with labeled headers into the prompt.
- **Prompt history:** persist each generator's inputs to `prompt_history`; every generator form has a "recent inputs" dropdown to refill. Cap 20 per feature.
- **Differentiation controls** (Monsha-style), available at generation time AND as post-generation refine actions on any AI draft: target level (class 1–12 / HSC / adult), Bloom's taxonomy level (remember→create), reading level (simple/standard/advanced), Translate to <language> (free-text, default Bangla), plus free-text custom instruction. Refines are stateless: current text + instruction → replacement draft.
- AI output always lands in an **editable draft** — AI never publishes directly. JSON-returning features validate with zod; on parse failure retry once with the error appended, then show raw text for manual use.

Features (each appears **only when a key is configured**):
- **Course outline generator (curriculum-first):** subject, level, duration (e.g. "HSC Physics 1st paper, 12 weeks") + optional syllabus/standards sources → JSON module plan (module titles, descriptions, per-module lesson titles with 1-line summaries). Rendered as an editable checklist; tutor unchecks/renames, then "Create" materializes draft modules + stub materials in the curriculum view.
- **Lesson plan generator (flagship — Monsha parity):** inputs: topic (or a stub material for module/course context), level, duration in minutes, language, **component picker** (checkboxes for each `plan_json` section: objectives, standards, vocabulary, hook, direct instruction, guided/independent practice, assessment, homework, differentiation), optional sources, optional standards from library to align to. Output: valid `plan_json` → opens in the structured lesson-plan editor as a draft. Per-section **regenerate** button (re-runs just that section with full plan as context). If standards were selected, AI must reference them in objectives; tagged automatically via `material_standards`.
- **Derived resources (context flows downhill):** from any lesson plan or material, one-click generate into the same module — **Lecture** (full markdown lecture draft), **Study notes** (summary/flashcard sheet), **Worksheet** (practice activities markdown, printable), **Quiz** (N questions of chosen types, draft, linked to module, standards tags inherited), **Rubric** (markdown criteria×levels table → `assignments.rubric_md` when generated from an assignment). Each generation includes the parent's content as source automatically.
- **Refine actions** on any AI draft: Expand / Simplify / Add worked examples / differentiation controls above.
- **Feedback draft:** on a submission, generate suggested feedback from assignment + rubric + submission text; tutor edits before returning.
- **Progress report narrative:** when generating a progress report (P10), optional AI paragraph summarizing the period from structured facts (attendance %, grades, quiz scores, completion) — tutor edits before sharing. Without a key the report is numbers-only, still complete.

Out of scope (do not build, even though Monsha has them): AI image generation, web-search "supplementary materials finder", slide/PPTX generation, Google Classroom/Drive export, standards auto-gap analysis beyond the coverage matrix.

- **Accept:** with no key: zero AI UI visible, all tests pass (lesson-plan editor still fully usable manually). Unit tests: crypto round-trip; JSON extraction/repair from fenced responses; OpenRouter + one other adapter request/response shape; URL-source text extraction; plan_json zod validation of mocked generator output (mock fetch — never call real APIs in tests). e2e with mocked provider: outline → skeleton in curriculum; lesson plan generated with component picker → editable structured draft → regenerate one section; derived worksheet + quiz from that plan land in same module; prompt history refills a form.

### P10 — Dashboard & Polish
- Tutor dashboard: today's sessions, ungraded queue (quiz manual-grade + submissions), outstanding/overdue billing, recent activity (from `activity_log`), quick actions.
- Student home: next session, open quizzes, due assignments, unread announcements, balance.
- Empty states everywhere, loading states, mobile-responsive pass, keyboard-accessible forms, error boundaries, 404s.

## 6. UI & Design System Guideline

The design language is inherited from **tutorapp.quest v1** (the whiteboard app in this repo at `tutorapp.quest/` — consult `src/index.css` and `tailwind.config.ts` as the reference implementation). v1 is "Miro/FigJam-inspired": warm paper canvas, glass surfaces, electric indigo brand, serif display type. v2 carries the same personality but adapted for a content-dense LMS: calmer surfaces, glass used sparingly.

### 6.1 Design tokens (copy into `globals.css` as HSL CSS variables, shadcn convention)

| Token | Value | Use |
|---|---|---|
| `--background` | `40 30% 97%` | App background — warm paper, never pure white |
| `--foreground` | `230 15% 12%` | Body text — near-black indigo, never #000 |
| `--primary` | `252 90% 62%` | Electric indigo — CTAs, links, active nav, focus ring |
| `--primary-glow` | `252 100% 75%` | Gradient partner: `linear-gradient(135deg, primary, glow)` for hero CTAs only |
| `--accent` | `168 76% 48%` | Teal — success states, "paid" badges, completion checkmarks |
| `--destructive` | `0 84% 60%` | Errors, overdue badges, delete actions |
| `--card` / `--popover` | `0 0% 100%` | Surfaces sit white on the warm background |
| `--secondary` / `--muted` | `230 20% 96%` | Subtle fills, table header rows |
| `--muted-foreground` | `230 10% 45%` | Meta text, captions |
| `--border` / `--input` | `230 20% 90%` | 1px borders everywhere; no heavy outlines |
| `--ring` | `252 90% 62%` | Focus rings match primary |
| `--radius` | `1rem` | Generous rounding is a signature — cards `rounded-2xl`, buttons/inputs `rounded-xl`, pills `rounded-full` |

Shadows (as CSS vars, from v1): `--shadow-soft` `0 1px 2px hsl(230 30% 10%/0.05), 0 4px 12px -2px hsl(230 30% 10%/0.08)` for cards; `--shadow-float` (deeper 3-layer, see v1) for popovers/modals only. No `shadow-md` defaults from Tailwind — always these.

Status color mapping (use consistently app-wide): draft = muted gray badge · scheduled = indigo outline · published/active/paid = teal · partial/due-soon/late = amber (`38 92% 50%`) · overdue/missing/failed = destructive.

### 6.2 Typography
- **Inter** (via `next/font`) for everything — UI, body, tables. Enable `font-feature-settings: "ss01", "cv11"` like v1.
- **Instrument Serif italic** as `font-display` — page titles, landing hero, empty-state headings, invoice/report headers. It is the brand's voice; use for display only, never body.
- **JetBrains Mono** as `font-mono` — invoice numbers, amounts in tables, codes, timestamps, and the v1 signature "meta label": `font-mono text-[10px] uppercase tracking-wider text-muted-foreground` for section eyebrows and table headers.
- Scale: page title `text-2xl font-display italic`; section heading `text-lg font-semibold`; body `text-sm`; meta `text-xs`. LMS screens are dense — default to `text-sm`.

### 6.3 Surfaces, motion, texture
- Default surface = white card, `rounded-2xl border shadow-soft`. **Glass** (`bg-white/70 backdrop-blur-xl border-white/60 shadow-float`) is reserved for floating chrome: sticky headers, the landing nav, modals. Never for content cards or tables.
- Backgrounds: auth pages and landing hero get v1's layered radial gradient (`--gradient-canvas`) + optional dot-grid (`radial-gradient(hsl(230 15% 70%/0.45) 1px, transparent 1px)` at `22px 22px`). App pages stay flat `--background`.
- Motion: v1's two entrance animations only — `anim-rise` (fade + 8px up, 0.45s) for page/card mounts, `anim-pop` (fade + scale 0.96→1, 0.25s) for popovers/toasts; easing `cubic-bezier(0.22, 1, 0.36, 1)`. Hover on interactive cards: `hover:scale-[1.02] transition-transform`. Nothing else animates; respect `prefers-reduced-motion`.

### 6.4 Layout & navigation
- **Tutor:** fixed left sidebar (collapsible to icons <1024px, bottom sheet on mobile): Dashboard, Students, Courses, Schedule, Billing, Announcements, Settings. Content area `max-w-6xl` with `p-6`. Page header row = display-serif title left, primary action button right.
- **Student/parent:** no sidebar — top bar (glass, sticky) with logo, Home / Courses / Billing links, avatar menu. Content `max-w-3xl` centered; feels like a feed, not an admin tool.
- Tables (billing, gradebook, attendance): full-bleed inside cards, `text-sm`, mono for numbers, sticky header, row hover `bg-muted/50`. On mobile, collapse to stacked cards — never horizontal scroll for primary flows.
- Forms: labels above inputs, `max-w-md` single column, destructive actions require an AlertDialog. Empty states: centered, display-serif one-liner + one primary action (v1 tone: friendly, not corporate).
- Print styles (invoices, lesson plans, progress reports): `@media print` — hide chrome, black on white, Inter, no shadows/rounding.

### 6.5 Landing page design (public `/`)
- Full-viewport hero on `--gradient-canvas` + dot-grid; glass sticky nav (wordmark left — "TutorLoft" in Instrument Serif italic, "Loft" in `text-primary`, like v1's TopBar; "Log in" button right).
- Headline in Instrument Serif italic ~`text-5xl/6xl`, one accent word wrapped in `text-primary` (v1 pattern). Sub-line `text-muted-foreground text-lg max-w-xl`. CTA row: primary gradient button (the only gradient-primary use) + ghost "Request access".
- Feature cards: three white `rounded-2xl shadow-soft` cards with lucide icon in a `h-10 w-10 rounded-xl bg-primary/10 text-primary` tile, mono uppercase eyebrow, short copy. `anim-rise` staggered.
- Keep it honest and small: this is a private tutoring app's front door, not a SaaS funnel — no fake testimonials, no pricing section, no cookie banner. Total page ≤ 2 screens tall on desktop.

### 6.6 Engineering conventions
- shadcn/ui components; Tailwind only (no CSS modules). Dark mode via `next-themes` optional — don't block on it.
- Server components by default; client components only for interactivity. Mutations via server actions with zod-validated inputs; return typed `{ok} | {error}` — no thrown errors reaching UI.
- Toasts via `sonner`. Dates rendered in the `timezone` setting (default Asia/Dhaka) with `date-fns`.
- Currency formatting helper `fmtMoney(minor: number)` reading the `currency` setting — used everywhere money is shown; mono font in tables.

## 9.5 Competitor Analysis (context for why features exist — informational, no tasks here)

Three competitor categories inform this spec. Where a competitor feature was worth stealing, it has already been folded into §5; this section records the reasoning and the deliberate omissions.

**Tutor business management (TutorBird ~$15/mo, Teachworks, TutorCruncher):** their core is scheduling + billing + parent visibility. Adopted: recurring schedule → auto-generated sessions, attendance-driven invoicing, prepaid session packages (their most common billing model), payment reminders, shared session notes for parents, calendar (ICS) feed. Omitted: payment-gateway collection (we track only, by design), tutor payroll and multi-tutor filtering (single-tutor app), CRM/lead pipelines, SMS gateways (we give copyable reminder text instead — free and works with WhatsApp).

**Classroom LMS (Google Classroom, Blackboard, Canvas, Moodle):** their core is content distribution + submissions + grading. Adopted: announcements with optional class comments, assignments with due dates/late flags/resubmission, rubrics shown to students, private submission comment threads, reusable comment bank, bulk-ish grading via the gradebook view, scheduled posting, standards tagging. Omitted: guardian email summaries (parents have real accounts here — stronger), practice sets/originality reports (AI-grading student work is out of scope), Meet/video integration, co-teachers, topic-based streams (modules cover it), mobile apps (responsive web).

**AI teaching assistants (Monsha, MagicSchool, Eduaide, Diffit):** their core is generation of teaching artifacts. We follow **Monsha's connected-workflow philosophy** (course → units → lessons, context flows into every generation) rather than MagicSchool's 80 disconnected mini-tools: adopted course outline generator, structured lesson plan generator with component picker, derived resources (worksheet/quiz/rubric/notes), differentiation controls (level, Bloom's, reading level, translate), source-material grounding, prompt history. Omitted: AI image generation, slides/PPTX export, web-search materials finder, 60-language marketing surface (translate-to-any-language covers the need), report-card-comment banks (our progress reports do this better with real data).

**Our wedge vs all three:** nobody combines tutoring billing + LMS + BYOK AI in one self-hosted-able, near-zero-cost app. Competitors are subscriptions ($15–30/mo + AI tiers); this app's marginal cost is a free Vercel/Turso tier plus the tutor's own API key. The progress report (real attendance + grades + AI narrative, shareable with parents) is the feature none of the three categories has end-to-end.
